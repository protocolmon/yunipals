# Restored-source READ143 admission

This is a new operation for the acknowledged original-pool5 restore epoch. It does not reuse the old c9 admission constructor, runtime binding, plan baseline or acknowledgement. The historical fc79 plan supplies only the exact 143 read statements: 109 SELECT, 20 EXECUTE and 14 USAGE. Existing role identities, LOGIN states, operational writes, Solana reads and both retained booster namespaces remain unchanged.

No production plan or new admission exists as part of this source preparation. The READ143, Arena and other permission requests remain separate authorization gates. A command argument is an exact scope check, not evidence that a person approved those permissions.

The new protected plan is created only after the actual Arena13 admission and its explicitly selected authentication phase pass the e82 context. The feature operation must still be absent. Initial review/commit/reconciliation also require the exact retained temporary YPAL source/API actors, private definition packets and boot inodes through de4's preservation leaf, including actual local/public serving GETs. These checks are separate from source-only and catalog-only current validation. The captured baseline includes the complete cd1 catalog and all explicit non-system column ACLs for every grantee, including PUBLIC and unmanaged roles. No column ACL change is owned by this operation. A proposed table SELECT is refused if the same relation and grantee already has any column SELECT, because PostgreSQL table REVOKE would remove that pre-existing column right. Unrelated existing column ACLs remain allowed and exact.

The fixed plan is `/var/backups/yunipals-ypal-restored-read-admission-input-v1-20261024/plan.json`. All operation records are new, exclusive root0600 files under `/var/backups/yunipals-ypal-restored-read-admission-v1-20261024`. Baselines, role graphs and detailed receipts are private and must not be published.

Run the installed owner as root with `python3 -I -B`, supplying the explicit protected e82 context input hash:

1. Default without `--plan-sha` is read-only plan review. `--capture-plan REVIEW_HASH` captures that exact fresh review once. Record the actual plan file hash.
2. Default with `--plan-sha ACTUAL_PLAN_SHA` reviews the pinned current baseline. `--rehearse REVIEW_HASH` executes the same guarded 143 statements inside one repeatable-read transaction ending in ROLLBACK. It proves the catalog, roles, all column ACLs, private inputs and retained actors were restored.
3. Only after separate exact authorization, `--commit REVIEW_HASH SQL_AUTH_SHA` makes one attempt. SQL_AUTH_SHA is SHA256 of the canonical JSON plus newline of the pure builder's 143-statement array. The durable intent precedes that attempt; the transaction guards the complete before and rehearsed after catalogs.
4. After an unknown outcome, never repeat commit. `--reconcile ACTUAL_COMMIT_INTENT_SHA` reads the exact owned postgraph and records `postgraph_reconciled_after_unknown_ACK`; it does not claim the missing original client acknowledgement was received and sends no GRANT.
5. `--inverse-review ACTUAL_ADMISSION_SHA`, then `--inverse ACTUAL_ADMISSION_SHA INVERSE_REVIEW_HASH`, removes only the owned 143 edges and requires exact catalog restoration. It refuses until downstream selectors/other owned changes have been restored. `--reconcile-inverse ACTUAL_INVERSE_INTENT_SHA` records a proven restored state without resending REVOKE. The inverse currently supports the initial temporary-feature phase only: it refuses if those exact temporary pack actors/configuration/boot have changed. A later feature rollback that restores new epochs needs a separately authenticated feature-inverse serving leaf before that phase can be admitted; this owner never labels new epochs as the old tuple. The inverse uses fbb's explicit acknowledged-active-or-terminal restored-source proof, never a forward readiness exception.

`validate_current(ackSHA)` authenticates the fixed new acknowledgement, derives only its pinned plan/context references, and requalifies the entire current143 graph plus active restored source. `admitted_components(ackSHA)` returns authenticated immutable records and static query primitives for a later owner that explicitly composes its own ACL extensions. `validate_receipt(ackSHA)` is the sanitized immutable-chain proof and explicitly does not qualify the current role graph or source actor. `validate_catalog_current(ackSHA)` separately verifies the actual current143/all-column catalog using static fbb query construction and explicitly qualifies no source actor, readiness or financial authority. A later owner must supply its own current writer proof after a managed transition. These APIs never turn a historical whole validator into a pass.

Validation is local only: focused Python lifecycle/filesystem controls and a disposable PostgreSQL16 fixture exercise the actual generated SQL, ROLLBACK, single COMMIT, foreign/PUBLIC table and column drift, retained LOGIN/read/write states and owned inverse. No host, provider, service, credential or production SQL actions are included.

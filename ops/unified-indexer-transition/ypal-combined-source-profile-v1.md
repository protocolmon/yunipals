Ponder0.17.5 separates raw synchronization cache from derived application state:

- `src/build/index.ts` hashes the evaluated `config.contracts`, accounts, blocks and ordering, then combines that with schema/indexing-function hashes. Changing these actual addresses/starts produces a different configuration identity, even if addresses come from environment variables. No actual new build ID is predicted here.
- `src/database/index.ts` refuses a different build in an already-used native application schema. The default path does not transfer the old build's derived checkpoint. Do not use a drop/reset, manually relabel `_ponder_meta`, copy a checkpoint or enable an experimental platform mode to bypass this check.
- The same physical database's `ponder_sync` stores blocks/logs/transactions and certified filter intervals independently of the application namespace. Unchanged contract/event filters can reuse matching intervals. Ponder's actual log-fragment key includes chain, contract address, topics and receipt requirements; it is not the native build ID. The focused test executes the actual installed fragment implementation and proves unchanged BNB keys remain equal while the old/new monster address keys differ.
- Fresh YPAL log coverage must be demonstrated for its own filters. The dedicated launch source may already have populated those filters if it uses the same physical sync store. Otherwise only missing intervals must be fetched. A generic chain-height gauge or old PROTO filter interval does not prove YPAL coverage. Wider certified filters can only be reused when the real interval store proves they cover the requested filter.
